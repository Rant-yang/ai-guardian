# 告警来源定位（更新至 2026-11-04）

## 当前能力展示（2026-11-05）

导航能力由 `adapter_contracts.py` 的服务端契约经展示目录传给控制台和悬浮窗，和动作监督能力分开。Qoder、Gemini、Ollama 目前不支持自动来源导航，界面直接说明，不展示可点击但没有实现的定位动作。来源 API 返回 unsupported，与已支持客户端的旧事件、缺失或过期定位信息区分。

支持导航的客户端仍是“请求返回”，不是可见会话已验证。请求处理中按钮显示进度且保持禁用，刷新不会解除同一事件的请求锁；开启隐私模式后返回的旧结果不进入界面缓存。接口已接受、终端已前置、具体标签页已显示仍是不同事实。

后续增加客户端导航时先实现并验证适配，再修改服务端契约；不能只添加前端名称或把 capability 标志当作真实执行验收。以下早期章节保留当时实现和证据范围；当前短期定位存储由 `locator_store.py` 持久化，可在有效期内跨守卫重启恢复，不再全部只保存在内存。


## 原控制台关联与实测补充

本轮修复了两个实际根因：终端窗口不一定是 Agent 的祖先进程；窗口恢复和前置也不一定同步完成。祖先定位无法唯一匹配时，使用一次性辅助进程关联源进程控制台，通过 `GetAncestor(GetConsoleWindow(), GA_ROOTOWNER)` 找到可见窗口。客户端自身拥有的传统控制台必须同时匹配 `ConsoleWindowClass`。保存控制台与窗口两套进程创建时间和句柄，点击时重新核对；窗口关闭、PID 复用或关联变化都拒绝跳转。辅助进程不读取标题、屏幕或对话。

窗口从最小化状态恢复后进行有界等待，再请求前置并检查实际前台窗口。OpenCode 同一实例连续点击不同事件时，旧的未完成导航被标为已替代，避免后续轮询又返回旧会话；已经发布给客户端的事件无法撤回。

本机 `scripts/probe_source_console.py` 创建两个独立临时控制台，成功捕获两个不同窗口，按反向顺序定位，两次均确认目标为前台窗口，随后关闭全部测试进程。报告位于 `.local/source-console-probe.json`。9 项窗口定位测试、6 项来源测试、5 项导航测试、4 项存储测试及 41 项后端集成测试通过；存储测试覆盖新增控制台关联跨重启保留。

这项实测证明独立控制台的关联与前置，不证明 Windows Terminal 标签页或 Codex 桌面会话已可见。新事件会建立新的关联，历史未捕获的窗口不能追溯补出。无需为这项后端修复重新安装钩子。

依据：[Microsoft Terminal 维护者关于控制台可见窗口的说明](https://github.com/microsoft/terminal/discussions/14492)。下面旧记录中“无祖先终端无法识别”已由本轮控制台关联回退部分改善，其余客户端会话确认边界仍适用。

## 2026-11-04 修复（以下早期记录以本节为准）

- 原生悬浮球和详情窗口在明确点击来源按钮后，调用固定的本地管理接口取得守卫 PID，再通过 Windows `AllowSetForegroundWindow` 授予后台前置权限。页面不能指定 PID、URL 或命令。本机自有原生窗口检查确认权限授予成功；不等于目标 Agent 标签页已经独立验收。
- OpenCode `navigation-2` 插件上报自身 PID，识别唯一关联终端；定位同时发出实例绑定的会话选择请求并尝试前置终端。后续状态刷新保留窗口回执。旧实例仍需在用户方便时重新打开以加载插件，不自动重启用户 Agent。
- 三类客户端的路由身份保存到 `.local/source-locations.sqlite3`，每类最多 2000 条、有效期 24 小时。包含原始会话 ID、OpenCode 实例 ID，以及可用时的终端 PID/创建时间/句柄；不含提示词、工具参数和凭据，不进入事件导出。清理对应历史会一并删除映射。该本地文件也不应对外分享。
- 重启后先恢复路由，再重新验证窗口进程创建时间和归属。OpenCode 还必须由相同实例重新心跳，不能转给另一实例。旧版未保存的事件无法追溯补出定位信息。
- 尚未完成：Windows Terminal 多标签精确选择、IDE 嵌入终端、无祖先终端的伪控制台，以及 Codex 桌面链接的可见会话确认。接口接受请求、窗口前置、会话显示分别描述，不能混为一项成功。

验证：41 项后端集成测试、64 项前端及插件测试；定位存储/过期/删除/重启专项测试通过。`.local/desktop-navigation-repair-check.json` 记录本机原生权限转移、详情事件匹配和透明面板检查。没有通过截图、模拟按键或向用户 Agent 发送提示词来验证。

Windows API 依据：https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-allowsetforegroundwindow

## OpenCode 实例定向定位（2026-11-03）

本机安装的 1.19.0 插件客户端有 `tui.publish`，没有 `tui.selectSession` 方法；独立服务实测支持 `/tui/select-session` 以及发布 `tui.session.select`。实现使用插件已有客户端的公开 publish 接口，只发送固定事件与已绑定会话 ID，不指定任意 URL，不调用 submit-prompt、execute-command 或权限接口。

插件在检查时附带随机实例 ID，原始会话及实例映射只留内存。管理页面点击来源按钮产生 15 秒有效、单次投递的请求。支持导航的插件约每两秒随心跳获取自己实例的请求；服务只接受匹配请求 ID 与实例 ID 的回执。其他实例不能领走这条请求，重复检查不重新绑定来源。成功回执仅表示 OpenCode 接口返回接受，不证明 TUI 可见，也不把终端自动前置。无图形 TUI 的 serve 模式同样可以接受事件。

需要重启已有 OpenCode 实例以载入插件更新，并有新的工具检查建立事件映射；不修改用户全局配置、不自动重启用户窗口。服务重启后旧映射失效，回退手动方式。原始窗口精确前置仍是未完成项；一个 OpenCode 服务接多个 TUI 时可能同时导航，不能宣称只激活某个窗口。

证据：`.local/opencode-navigation-probe.json` 的 guardian_bridge 为 queued→dispatched，visible_session_verified=false，模型请求数 0。验证脚本 `scripts/probe_opencode_navigation.py` 使用临时配置、空会话和隔离 Guardian。冷启动曾超过 35 秒，成功验证使用 120 秒初始化预算；不代表该客户端冷启动性能已经达标。


## Claude 关联终端前置（实验）

2026-11-03 扩展至 Codex CLI：Codex 钩子同样只附带自身 PID，复用唯一祖先终端捕获与激活检查。有已捕获终端线索时优先返回终端，不启动 Codex 桌面 URI；即使该窗口后来关闭或身份变更，也只返回手动 `codex resume <会话>` 方式，不把 CLI 会话转到桌面。无终端线索的 Codex 动作仍使用现有桌面会话链接，无法据此区分所有 CLI/桌面运行形态。该扩展尚未通过真实可见终端和标签页验收。

执行前钩子只额外上报自身 PID，服务读取最多 10 层父进程的进程名、父 PID 和创建时间；不读取命令行、窗口标题、屏幕或对话。只有找到唯一可见终端窗口时记录内存映射。支持 WindowsTerminal/OpenConsole/conhost 的祖先窗口模式；IDE 内终端、伪控制台隐藏窗口、终端与 CLI 无父子关系、多窗口共享进程都可能无法识别。

仅用户点击来源定位时调用窗口前置，重新检查进程创建时间、可见窗口归属和唯一性，并查询 GetForegroundWindow。系统拒绝前置时显示未确认，不通过模拟按键或改系统设置强抢焦点。前置成功只证明终端窗口，不证明其当前标签页或 Claude 会话。PID 是钩子提供的关联线索，并非客户端身份认证；不把此线索用于权限或执行决策。窗口句柄生命周期没有独立事件监视，不能声称绝对不会误定位。

映射不进 SQLite 或导出，按事件绑定且重复检查不可改绑，随历史清理、24 小时到期或服务重启失效。原始会话标识沿用现有短期内存策略。没有额外安装全局插件、修改客户端模型或执行备用命令。

目前完成模拟 API 的唯一性/过期/PID 复用/系统拒绝测试，以及本机真实 Win32 自身 PID、父 PID、创建时间查询。仍需用户实际终端形态的前置与标签页验收，不能据此宣布统一原窗口体验完成。

依据：[Windows 前台窗口限制](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)、[进程基本信息接口](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntqueryinformationprocess)。后者可能随系统变化，调用失败时退回手动定位。

本机后台测试进程连续 20 次只读探测均未匹配终端（符合其后台启动方式），平均约 1.373 ms，没有激活窗口；这是有限路径耗时，不代表所有终端形态的延迟上界。新增 PID 字段后的 Claude 真实 CLI 打印/合成拒绝/返回信号三例再次通过。

## 手动恢复入口

Codex 桌面链接路径也保留由已校验 UUID 生成的 `codex resume` 备用命令；系统协议失败时明确提示需要已安装的 Codex CLI，不能把命令可用性当作该终端实际存在。完整详情提供“复制恢复命令”，仅在用户点击时写入剪贴板，不启动进程、不批准或重试动作。剪贴板不可用时保留可选择的命令文本。原始会话 ID 会随明确复制进入系统剪贴板，其生命周期由操作系统管理。

切换事件、进入回放或开启隐私模式后，旧复制及定位按钮拒绝工作；无来源信息时不展示复制入口。54 项前端与 6 项来源定位回归通过，包括协议失败仍保留命令、无隐式复制、剪贴板失败和过期交互。未操作用户真实剪贴板，也未验证每种 WebView/浏览器的剪贴板授权；拒绝访问时使用文本备用方式。本轮未重启后台，以保留当前临时来源映射；Python 变更待下次统一重载生效。


## Pi 来源与持久会话恢复（2026-11-05）

Pi 扩展上报自身 PID 和是否具备持久会话文件的布尔标记，不发送会话文件路径或正文。服务器按原事件绑定完整会话 ID，复用唯一关联终端捕获/前置检查；无法识别终端时保留手动方式。元数据单独存入 24 小时定位存储，可跨守卫重启恢复，不进入事件导出或授权依据。重复事件不得改绑来源。

只有明确持久化、格式受限的会话 ID 才生成 `pi --session <完整 ID>`。必须在原项目目录和相同 Pi 配置、会话存储环境中手动运行；跨目录可能提示分叉。临时会话不生成命令；不自动启动恢复、不发送消息、不重试工具。末尾 `.jsonl` 会被 Pi 作为路径解释，因此不给这种自定义 ID 生成命令。

依据 Pi 1.5.0 随包官方 cli.md、rpc-commands.md、main.js 的 resolveSessionPath，以及 [官方 CLI 文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/cli.md)。真实隔离验证先保存会话，再通过 `--session` 启动 RPC 只读 get_state，确认返回原完整 ID 且没有额外模型请求；与其余九个执行场景一同通过。此项不证明所有存储配置、终端窗口或标签页的可见返回已验证。来源能力标为关联终端尝试，不是精准标签页确认。
